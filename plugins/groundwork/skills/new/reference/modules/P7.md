# P7 External dependencies

## When on
Profile check P7 is "yes": there are external dependencies that may change or disappear, such as payments · chain · auth SDKs · data providers. Signal words: payment provider · auth SDK, blockchain · wallet, external data provider.

## Questions (one message)
First show, in one message, the dependency list drawn from the stage 1 summary and the recommended handling per dependency (adapter · exit plan). End with "as recommended, or just the numbers to change". Ask only the changed numbers, separately, to the end.

1. **List of dependencies that may change** — recommended: list payments · auth · chain · data providers · hosting one by one, each with a one-line role. Reason: no one watches key expiry and terms changes of a dependency that is not on the list.
2. **Boundary** — recommended: one port/adapter layer per dependency in `adapters/<name>/`; app code calls only the neutral interface and can swap in a fake implementation. Reason: once a provider's name spreads through the whole codebase, replacing it means a rewrite.
3. **Exit plan** — recommended: per dependency, one line each for the replacement candidate · switch order · start signal (price · terms · outage thresholds), and a kill switch. Reason: looking for an alternative after it is gone is too late.

## CLAUDE.md rule lines
- Call external dependencies only through the neutral interfaces in `adapters/`, and never use a provider's name in identifiers outside the adapter.
- A new external dependency first gets one line in `docs/vendors.md` (key location · expiry · limits · cost · terms · owner) and an `external-<name>` ADR. Never write key values down.

## Scaffold
- The `docs/vendors.md` register (`templates/docs/vendors.md`): key location · expiry · limits · cost · terms · owner · exit.
- The adapter folder and, per dependency, an interface file · 1 fake implementation. The fixtures the fake returns are made by recording a real response once, with the recording date in the file head (no made-up shapes). If there is no key · account yet, use the example response from the provider's docs, write `not recorded — record after the first key is issued` in the head, and add the recording as a plan task (record only with staging · test keys — never a prod key).
- (Dependencies you read from, such as data providers) the adapter records the last success time per source and counts odd responses such as 0 rows · "HTTP 200 but HTML" as failures. When the threshold time has passed since the last success or consecutive failures pass the threshold, it calls the B11 alert function (a stalled source is silent). Test that path with the fake too: odd responses count as failures, and a source past the threshold calls the alert.
- Per dependency package, a check that catches imports outside the adapter and fails (`reference/baseline-scaffold.md` 'Boundary import check'). The fake does not import the SDK either.
- Do not rebuild what the baseline (secret scanning · the secret rotation runbook) already does.
