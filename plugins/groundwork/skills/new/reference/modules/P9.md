# P9 Money-moving keys

## When on
Profile check P9 is "yes": the server or an operator holds a key that can **send assets to destinations not fixed in advance**, or a key that signs **values that decide where money goes** (settlement results · prices · oracle values) — hot wallet · server wallet private keys, contract deploy · admin keys, payout · transfer API keys, settlement result · price signing keys. **Or** the app front end (web · native app) opens withdrawal · transfer · sell · order signing through the user's session · wallet (an embedded wallet in the app included) — this is called a "user-money action" (it turns P9 on even without an operator key). Signal words: wallet · hot wallet, contract deploy · admin, withdrawals · payouts · transfers (sending money to users), sell · order signing, signing settlement results · prices (oracle).

Alongside P1 (are the quantities exact?) · P7 (can the dependency be swapped?), it covers **keys and limits**. The three are often on together.
- A payment provider key that can only refund (money returns only to the original payment method) belongs to P7, not P9 (the payment provider key line of ADR `external-dependency`).
- "Token" · "refund" are not signal words — they overlap with design tokens · auth tokens and would wrongly turn P9 on through the "unclear → yes" rule.

## Questions (one message)
Show them at once as a numbered list and end by asking "as recommended, or just the numbers to change". Ask only the changed numbers, separately, to the end. Without a contract, drop item 4. Without an operator key (a dapp that uses only user wallets), drop items 1–3. Renumber the remaining items from 1.

1. **Key table and signing location** — recommended: for each key that moves money or decides where money goes (settlement results · prices), write in a table what it can do · where it is kept · the code path that uses it · the source of the values it signs. Wallet keys sign inside a cloud key management service, and the raw key never sits in a file · environment variable. Every signing path passes a deterministic check inside the signing adapter right before signing (target · function selector · value range · state — e.g. an already settled result is not signed again). Results · prices never use the value the caller gave as it is; they are signed only when they equal the value fetched again from a source the caller cannot write (chain · external data) — if the source is a human judgment, sign only after a second approval with a different credential (second factor), and read the state from that source too. A payout API key is a restricted key with payout permission only, in the secret store. Reason: if the raw key is on the server, the moment one server is breached it is the whole balance, and if the signing adapter trusts its caller (admin screen · DB row · webhook), breaching just one of them gets any result signed.
2. **Limits and balance caps** — recommended: hourly · daily transfer total limits. Keep only one day's operating amount in the balances the server can send from (hot wallet · payout account), and the rest somewhere the server cannot move it. Over a limit: reject and mail. Also set, as an amount, above how much entrusted money an external audit is called in. Reason: even if noticing takes hours, the loss is bounded by the limit.
3. **Admin actions that move money** — recommended: go through a second factor, and pick receiving addresses only from a pre-registered list (never build "send to any address" in the admin API). Right before signing, verify the amount · receiving address · chain id · purpose again. Reason: once one admin session is hijacked, the admin API becomes a withdrawal window.
4. **Contract permissions** (only with a contract) — recommended: split operating · withdrawing · adding admins into different roles, make it impossible for admins to remove each other, keep a separate emergency pause role, and write the role table before deploying. Reason: if everything is mixed into one admin role, one key is everything.
- (only with user-money actions, added as the next number) **User-money actions** — recommended: ① Put the off-page gate where the signature goes (branches below; with several money actions, per action). ② If silent signing (signing without a confirm dialog) is needed, a scoped session key (contract · function · limit · expiry) instead of the full key. ③ Keep the external code that runs on the page origin on a list and cut it down: no session replay, analytics server-side first, social embeds in sandboxed iframes. A native app cuts the external SDKs bundled into the app (analytics · error reporting · ads · session replay) down with the same list — CSP · nonce · signal 7 · the external-script flag · runbook E are web only (web screens inside a webview shell are web). Signing requests are human-readable structured data (EIP-712). Reason: if one script on the page origin or one SDK bundled into the app is compromised, it skips the app screen's confirmation · step-up and calls the signing function directly or fakes clicks (in a native app, the 'page' is the app process). A gate that works has to sit outside the page (our server · the wallet confirm dialog · the wallet provider's server), and if a vendor on the allowlist is compromised, CSP · SRI cannot stop it either. The message shows only the branches that apply.
  - **Goes to our server** (orders · withdrawal requests · gas sponsorship): an action that sends money out runs only with a step-up token the server verifies, and the server also checks value ranges on orders · transfers that come in with a user signature (price range against the market price · quantity limits, including money values that must match contract caps, such as fee rates · limits). Gas sponsorship narrows the sponsorship policy to your own contracts · functions and adds a server check (when the platform supports it; if it cannot, the hardening table).
  - **An external wallet (browser extension · mobile wallet app) calls the chain directly:** the server gate is `n/a` — the confirm dialog is in the wallet, outside the page. Instead: signing requests are structured data, approve covers only the amount that transaction uses (never unlimited), and for our own contract, per-transaction · daily caps on the contract side.
  - **An embedded wallet calls the chain directly:** put the wallet provider's server-side policy in place as the gate — allowed contracts · functions · amounts and step-up at signing (e.g. Dynamic Policies & Rules · Action-based MFA, the Privy policy engine (wallet `policy_ids`, TEE execution environment) · wallet MFA). The provider's docs may not say clearly whether the policy also applies on the path where the user signs directly, or whether a user session can remove the policy, so check in the provider's test environment that a transaction outside the policy is not signed · that a user session cannot remove or change the policy · that the private key cannot be exported to get around the policy (if even one of these gets through, bind our server in as a co-signer (e.g. a Privy key quorum) and go to the server branch; if that cannot be done either, `not possible — hardening table`). Per Privy's docs, the owner can change a wallet's policies ("update the policies assigned to a wallet"), and an update request passes with a signature from the key bound to the user. Private key export is also open to the owner until it is blocked with a `DENY` rule (`exportPrivateKey`). So for a wallet the user owns, the policy may not work as a gate (not measured). With Privy, copy `<skill-dir>/tools/privy-check.mjs` to a temporary folder outside the project, install `@privy-io/node` (a Privy test app is needed), and look first at A3 (does a user session remove the policy) · A5 (does it export the private key); if they get through, look at B (owner = app key + user 2-of-2, the user being a signer with a policy attached). Write the result in the embedded-wallet policy measurement line of the hardening table. If the provider has no policy, write `not possible — hardening table` and put it in place before checkpoint 3 (when real money first flows), without fail.
  - **(native app · webview shell) OTA:** use EAS Update during development, and before the production build that opens real money (required before checkpoint 3), turn OTA off (`updates.enabled: false`, free) or put code signing on (EAS Production plan or higher, private key outside CI). Which of the two is picked at that time. Reason: if `EXPO_TOKEN` leaks, JS can be pushed to every installed app to call the signing function directly.
  - The wallet kind is read from the stage 2 stack answer. If unknown, show the embedded branch and add one line at the end of this item: "Wallet — recommended: an embedded wallet (a wallet service such as Privy · Dynamic). If it is an external wallet (extension · app), let me know."

## CLAUDE.md rule lines
- The operator's keys that move money or decide where money goes (settlement results · prices) are only those in the ADR `money-keys` key table (adding one starts with the ADR), and operator signing happens only inside the key management service. Never keep a raw key in files · environment variables · logs.
- (only with an operator key) A transfer must pass the limit check, and the receiving address is picked only from the registered list. Never build a transfer to an arbitrary address as an admin action.
- (only with an operator key) Operator signatures that decide where money goes (transfers · settlement results · prices) pass the deterministic check (target · function · value range · state) inside the signing adapter (the payout adapter if there is only a payout API), and results · prices are signed only when they equal the value fetched again from the source in the key table (for a human judgment, only after the second approval) — never sign on trust in the caller.
- (only with user-money actions) An action that sends user money out goes through the off-page gate of ADR `money-keys` — never open it on the app screen's confirmation alone. External scripts on the page origin (for a native app, external SDKs bundled into the app) are only those on the ADR `money-keys` list.
- (only when a user-money action passes through our server) That action goes through a step-up token the server verified and a value-range check.
- (only when a user wallet calls the chain directly) Build signing requests as human-readable structured data (EIP-712), and approve opens only the amount that transaction uses (never unlimited). With an embedded wallet, never build a transaction outside the provider's server-side policy (ADR `money-keys`).
- (only a native app · webview shell with user-money actions) A production build that opens real money first meets the OTA condition of ADR `money-keys`.

## Scaffold
- The signing adapter interface and a fake implementation (the builder writes the real key management service implementation for the stack). With only a payout API, the limit check and the pre-payout check on the payout adapter, with tests: reject anything already paid out or revoked · amounts out of range · unregistered recipients.
- The pre-sign check inside the signing adapter, with tests: reject signing for targets · functions outside the allowlist, reject signing a result whose state does not fit (already settled), reject when a result · price the caller gave differs from the value fetched again from the source (the fake), and also reject a result whose source is a human judgment but that has no second approval.
- The limit check function, with tests: just under the limit passes · over it is rejected · concurrent requests are summed.
- The receiving-address allowlist check, with a test.
- One switch (a config value) that stops actions that send money out, with a test: when off, transfer · withdrawal requests are rejected.
- Without an operator key, do not build the signing adapter · limits · address list — only the stop switch and the user-money action item below.
- (user-money actions) A web front end gets a flag that loads external scripts from one place and turns them off, with a test (when off, the page has no external scripts). CSP follows the section A security row of `reference/client-forms.md` (a money front end uses nonce + `'strict-dynamic'`; violation reports are B11 signal 7). A native app builds no flag · CSP (external SDKs are bundled into the app and cannot be turned off at run time — cut them down with the ADR list). Gate tests only for the branches in use: server branch — reject withdrawal requests whose step-up token is missing or fails verification · reject orders outside the value range / external-wallet branch — a test that the function building signing requests builds only structured data and never an unlimited approve · (contract) reject over the cap / embedded-wallet branch — keep the provider policy as code (config file · API call), and write in the spec the procedure for checking in the provider's test environment that a transaction outside the policy is not signed · that a user session cannot remove or change the policy (unit tests cannot see the provider's server).
- (contract) Role tests: the operating role cannot withdraw · add admins, an admin cannot remove another admin, and while paused no transfer goes through.
- (with only a contract repo and no server) An hourly GitHub scheduled workflow reads events · balances over a public RPC and fails when a threshold is passed — the failure mail is B11 signal 6. Chains · tools differ per project, so there is no template; pin the actions to commit SHAs per B10.
