# P2 Multiple instances and async

## When on
Profile check P2 is "yes": there are two or more servers, or scheduled jobs · workers · queues. Signal words: scheduled jobs · cron, workers · queues, several servers.

## Questions (one message)
Show them at once as a numbered list and end by asking "as recommended, or just the numbers to change". Ask only the changed numbers, separately, to the end.

1. **Instance assumption** — recommended: assume there are always 2 or more instances (from day one). Reason: scheduled jobs and state transitions built on a 1-instance assumption run twice the moment there are two.
2. **Running jobs** — recommended: every scheduled job · queue consumer goes through one shared runner (distributed lock + idempotency key + writes tied to the claim row). Reason: if each job writes its own locking, the place that misses it becomes the incident.
3. **Splitting web and workers** — recommended: one codebase, with roles split by `ROLE` (api | worker | scheduler) from the start. At first they may all run in one container. Reason: if public request handling and the core background loops share one process, a memory incident in the API stops the whole business.
4. **Long-running flows** — recommended: set, per state, a deadline and a cleanup job, an outbox for messages to send, idempotency for received messages, a reconciliation job (pull) and operator actions. Reason: if a flow relies on one notification alone, missing it once stalls that flow forever.

## CLAUDE.md rule lines
- Assume there are always 2 or more instances. Register scheduled jobs and queue consumers only through the shared job runner; never register a bare `@Cron` · `setInterval` · APScheduler directly.
- Every non-terminal state of a long-running flow has a deadline and a cleanup job. State transitions only move forward through conditional updates, and received messages are filtered by idempotency key.

## Scaffold
- The shared job runner skeleton (distributed lock + idempotency key + writes tied to the claim row; per run a time limit · max retries · cancel; for calls that cost money, a per-run cost cap) — the builder writes it for the stack. The role-branching (`ROLE`) entry point.
- A check that catches bare scheduled jobs outside the runner and fails. Copy `templates/gates/rg-none.sh` to `scripts/`; example (adjust to the stack): `bash scripts/rg-none.sh -n '@Cron\(|setInterval\(|node-cron|add_job\(|BackgroundScheduler' src --glob '!**/job-runner/**'`. This helper passes only when rg finds nothing; it fails with 1 when it finds something, and with 2 when rg is missing or the folder · pattern is wrong. Being one command, it hides no failure before or after it wherever it sits in the `&&` chain of the one-line gate `{{cmd_check}}` (`! rg` passes even when rg is missing or the folder is wrong, and comparing rg's exit code after `;` buries the failure of the step before — use neither).
- The skeleton of one reconciliation job and a slot for the outbox table. Do not rebuild what the baseline (CI · health) already does.
