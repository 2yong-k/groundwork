# P6 Multiple apps

## When on
Profile check P6 is "yes": besides the user app there are more apps, such as admin or docs. Signal words: admin · back office, docs site, two or more apps.

## Questions (one message)
Show them at once as a numbered list and end by asking "as recommended, or just the numbers to change". Ask only the changed numbers, separately, to the end. Without an admin app (a docs site only), drop item 3.

1. **Brand · token source location** — recommended: keep it in one place and let the apps take it from there. A single repo uses a workspace package; in umbrella mode one UI repo holds the source and the other repos copy it with `sync-tokens.sh`, checking drift by the source hash (no registry · git dependency). Reason: if each app keeps its own copy, colors and fonts silently drift apart from app to app.
2. **Contract types** — recommended: generate types from one schema (one of DB schema · OpenAPI · Zod) and share them; never copy them by hand. Reason: hand-matched types still compile when only one side changes.
3. **Admin actions** (only with an admin app) — recommended: no generic table editor · generic proxy, only named action paths (money · state tables too change only through named actions). Every admin path (GET included) sits behind one wrapper (session · admin allowlist re-read on every request · role · Origin of writes · environment match · one audit-log line), and the confirm dialog shows the result that will change (results to be settled · amount to send · count to delete). If a proxy is truly needed, use a path allowlist and check the character set of id fields on the decoded value. Reason: a tool that edits tables directly skips deletion procedures · audit · confirmation; one path missing from the wrapper can be read without login or write to another environment; and if the allowlist is read only at login, a removed admin keeps writing until the session ends.

## CLAUDE.md rule lines
- The design token source lives in one place only (`{{token_source}}`), and apps never edit their copies directly. A change flows source → generate → each app, in that order.
- Types that pass between apps are only those generated from the single schema.
- (only with an admin app) Admin actions are built only as named paths — no generic table editor · generic proxy. Every admin path (GET included) passes one wrapper (session · admin allowlist re-read on every request · role · Origin of writes · environment match · audit log), and the confirm dialog shows the result that will change.

## Scaffold
- Shared tokens: a single repo uses a workspace package. In umbrella mode one UI repo's `design/tokens.json` is the source; the other UI repos copy it with `templates/gates/sync-tokens.sh` and tie `--check` into the gate (source hash comparison; SKIP in CI, where the source is absent).
- Contract type generation check: regenerate the types from the schema and fail if they differ from the committed result.
- (admin app) One admin path wrapper (no session 401 · admin allowlist · role re-read on every request, otherwise 403 · Origin mismatch on a write 403 · environment mismatch 409 · one line through the B11 audit-log write function) and two tests (a removed admin's existing session gets 403 on the next request; a non-admin session gets 403 too), plus a route list test: collect the route files and pin that every admin path (GET included) passes the wrapper and that the exceptions are only those written in the test. With a proxy, paths outside the allowlist get 403, plus a test that rejects `..%5C` · `%2e%2e` (checked on the decoded value).
- Do not rebuild what the baseline (CI · lint) already does.
